# Spec-Driven Development (SDD) Workflow

Фреймворк для разработки с помощью ИИ-агентов, исключающий хаос «вайб-кодинга» через фиксированные спецификации, пошаговое планирование и автономное исполнение.

---

## 🚀 Быстрый старт (Ручной режим без CLI)

Поскольку сторонние установщики не требуются, вся логика SDD держится на локальных Markdown-файлах и скиллах для Claude Code.

### 1. Структура проекта
Создай в корне репозитория следующие папки и файлы:

```text
.
├── .specify/
│   ├── memory/
│   │   └── constitution.md     # Архитектурные правила и стандарты качества
│   └── templates/              # Шаблоны для спек, планов и тасок
├── .claude/
│   └── skills/                 # Скиллы для Claude Code (слэш-команды)
└── specs/                      # Рабочие спецификации фич
```

### 2. Рабочий пайплайн (Вызов в чате Claude Code)

Выполняй команды последовательно. Каждая фича проходит 5 строгих этапов:

1. **Конституция (один раз на проект):**
   > `/speckit-constitution`
   > *Задача:* Создать свод правил проекта (требования к чистоте кода, архитектуре, обработке ошибок и тестам). Сохраняется в `.specify/memory/constitution.md`.

2. **Спецификация (`spec.md`):**
   > `/speckit-specify`
   > *Задача:* Описать **что** и **почему** мы делаем. Фокус на User Stories и критериях приёмки (Acceptance Criteria), без технической реализации. Сохраняется в `specs/<номер-фичи>/spec.md`.

3. **Технический план (`plan.md`):**
   > `/speckit-plan`
   > *Задача:* На основе спеки спроектировать стек, модели данных, архитектуру и контракты. Сохраняется в папку фичи.

4. **Декомпозиция задач (`tasks.md`):**
   > `/speckit-tasks`
   > *Задача:* Разбить техплан на атомарный чек-лист мелких задач с правильным порядком зависимостей.

5. **Реализация и тестирование (`Implement & Converge`):**
   * *Лайфхак:* Очисти контекст чата (начни новый диалог), чтобы сэкономить токены.
   > `/speckit-implement`
   > *Задача:* Поочередно выполнить задачи из чек-листа, написать код и запустить тесты до статуса `Converged`.

---

## 💡 Архитектурные принципы SDD

* **Спека как источник правки:** Код — это вторичный артефакт. Если нужно изменить логику системы, правка вносится в `spec.md` и `plan.md`, а не «на лету» в чате.
* **Изоляция контекста:** Проектирование (дорогие модели / максимальное внимание) отделено от чистого написания кода по чек-листу (более быстрые/дешевые модели).
* **История решений в Git:** Все требования, планы и чек-листы коммитятся в репозиторий. Через полгода любой разработчик (или ИИ) поймет, *почему* код написан именно так.
